# Go API template SOP audit

This ledger applies only to the repository rooted at
`/root/code/go-api-template`. Evidence from generated services, platform
services, sibling repositories, or historical green builds does not establish
compliance for this repository.

The source of truth is `AGENTS.md`. A feature is `verified` only after its
applicable contract, authentication, authorization, logging, cache, lock,
optimistic-lock, audit, presentation, observability, unit-test, integration-test
and shared-component decisions have direct evidence in this repository.

Status values:

- `pending`: not yet inspected against the complete SOP.
- `in_progress`: inspected, but evidence is incomplete or gaps remain.
- `verified`: every applicable SOP concern has direct implementation and test evidence.
- `not_applicable`: reviewed infrastructure concern with a recorded rationale.

## Configuration profile audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Contract | `config.LoadWithProfile(path, explicitProfile)` is the single loader for API and migration binaries. An omitted path discovers `config.*` in the current directory and then `./config`; an explicit missing or malformed file fails. |
| Precedence | Defaults are installed first, then the base file, sibling `config-{profile}` file, `APP_*` environment values, and finally the explicit `-env` profile. Existing tests prove profile-before-environment behavior, environment list decoding and explicit profile selection. |
| Runtime context | `Config.Runtime` exposes the normalized active profile and only the files actually loaded. HTTP and unary/stream gRPC middleware place that profile in request context, and the root logger and OTel resource carry it. |
| Validation/security | Configuration validates dependency relationships and production restrictions before Fx starts. Secret fields are blank in committed YAML. Production now fails closed without gRPC TLS, disabled reflection, JWKS-based authorization, an asymmetric JWT signing key, and the durable event/operation/security-log chain. |
| Logs/cache/locks/audit | Not applicable to the loader itself: it performs no business mutation and owns no persistent or cached state. It supplies bounded settings to those components. |
| Presentation | Profile names are normalized to lowercase and validated; loaded paths remain diagnostic runtime metadata and are not exposed as business data. |
| Tests | Unit tests cover file/environment/profile precedence, current-directory discovery, defaults, shipped development/test/production profiles, asymmetric JWT pairing, PSK length, migration dependencies, authorization dependencies, outbound credential transport, lifecycle bounds, production fail-closed rules, and HTTP/unary/stream gRPC profile propagation. `go test`, race tests, vet, lint, Swagger/Proto drift, Compose validation and the integration-test policy gate pass. |
| Shared capability | Uses Viper and mapstructure rather than a local parser. Both API and migration commands reuse the same loader. |

## Dependency injection and lifecycle audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Dependency graph | `app.New` composes named Fx modules and constructor injection; no service locator or mutable global container is used. The graph test now performs a real `Start` and `Stop`, rather than checking only `App.Err`. |
| Startup ordering | Automatic migration is invoked before database-backed transports are constructed. HTTP/gRPC listeners are bound in lifecycle hooks, so bind failures are returned to Fx. Route synchronization and initial policy compilation finish before serving traffic. |
| Owned resources | Logger, SQL pool, Redis client, NATS connection, outbound gRPC connections, JWKS verifier and trace provider register Fx stop hooks. Fx reverse hook order stops consumers and servers before their dependencies. Constructor failures close resources already created within that constructor. |
| Background work | File deletion, data lifecycle maintenance and route-policy refresh use `background.Worker`; cancellation is followed by a bounded join using the Fx stop context. HTTP starts its policy worker only after the listener binds, preventing a failed start from leaking the worker. |
| Event consumers | The shared `eventbus.RegisterConsumer` adapter runs the SDK's blocking consumer outside `OnStart`, reports unexpected exits, and cancels and joins it during `OnStop`. This fixes the prior startup deadlock when operation/security logging was enabled. |
| Shutdown | HTTP uses `Server.Shutdown`, gRPC attempts `GracefulStop` and falls back to `Stop` on deadline, cron waits for running jobs, and all managed workers honor the configured Fx stop timeout. |
| Tests | Unit tests prove managed-worker cancellation, deadline behavior, stop-before-start safety, asynchronous consumer start and joined shutdown. App tests exercise the complete Fx graph through actual start and stop. Targeted unit, race and vet gates pass. |
| SOP applicability | Lifecycle infrastructure performs no business mutation and owns no API presentation, authorization, cache or audit-record decision. Its responsibility is deterministic construction, failure propagation and teardown. |

| --- | --- |

## Database, transaction and migration audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Dialects and database selection | Runtime connections support PostgreSQL and Kingbase through pgx and MySQL through go-sql-driver/mysql. `database.name` overrides the DSN database. PostgreSQL/Kingbase set `search_path`; clients and sessions use Asia/Shanghai / `+08:00`. |
| Pool safety | Enabled databases require a bounded positive open-connection count, a non-negative idle count no greater than open connections, positive lifetime/idle limits and a positive ping timeout. Opening performs a bounded ping and closes on failure; Fx closes the pool on shutdown. |
| Transactions and audit actor | All domain writes use `Transactor.Within`, which rejects a missing principal. PostgreSQL/Kingbase use transaction-local `set_config`. MySQL uses its connection variable only while the transaction is active and now clears it before commit and before rollback, including cancellation and panic paths, preventing pooled-connection identity leakage. |
| Audit schema | A migration contract test scans all three dialects and requires every created table, including associations, to contain the seven canonical audit/version/soft-delete fields. PostgreSQL/Kingbase require `app_enable_audit`; MySQL requires insert/update triggers and delete guards except append-only log retention tables. |
| Trigger behavior | PostgreSQL/Kingbase fail writes without `app.actor_id`, preserve creation metadata, own timestamps and version increments, maintain delete metadata and reject physical delete. MySQL audited columns are non-null and trigger-owned; operation/security logs deliberately permit physical deletion only for bounded retention maintenance. |
| Migration isolation | golang-migrate receives the generated service-specific history table. PostgreSQL/Kingbase receive the configured database and search path; MySQL receives the configured database. Optional schema creation is identifier-validated and serialized by a database advisory transaction lock. Unknown directions are rejected before opening a database. |
| Startup and CLI | The same migration runner is used by Fx automatic startup migration, the dedicated versioned migrate binary, Compose migration jobs and Kubernetes migration Job. Startup failure prevents transports from serving. |
| Tests | Unit tests cover DSN/database/schema options, timezone parameters, schema bootstrap locking, audit DDL, actor requirements, commit/rollback behavior, MySQL actor cleanup and migration direction. The integration suite exercises concurrent up, service-owned history, CRUD/transactions, triggers, optimistic locking, retention and full down on PostgreSQL and MySQL. Both the `verify` and Testcontainers `integration` jobs passed in GitHub Actions run `35037858673`. |

## HTTP contract and middleware audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Contract | All registered `/api/v1` business routes use POST; file upload is the documented multipart exception. Success and failure use `{code,message,body,request_id}`. Standard GET endpoints are limited to operational/browser protocols such as probes, metrics, JWKS, Swagger and pprof. |
| Error codes | Local HTTP errors alias the authoritative `microservice-platform-go/errorcode` registry; a test fails if a used code is not globally registered. HTTP statuses remain semantic. Unknown routes, wrong methods and trailing-slash variants now return the common envelope instead of Gin redirects/default bodies. Technical causes remain server-side. |
| Request identity | A syntactically bounded incoming `X-Request-ID` is accepted; an invalid or absent value is replaced with a generated ID. It is written to the response header, request context, logs and every common response, including timeout and routing errors. |
| Cancellation and bounds | The request context receives the configured deadline and retains net/http client-disconnect cancellation, which context-aware SQL, Redis and upstream adapters consume. Read/write/idle/request timeouts and body size must be positive and bounded before startup; `MaxBytesReader` enforces the body ceiling. |
| Input protocol | Non-empty POST bodies require `application/json`; the file upload route alone accepts multipart form data. Invalid JSON is translated through shared error handling. Idempotency keys are validated, echoed and context-propagated. |
| Browser/network security | Trusted proxy parsing is delegated to Gin and invalid entries fail server construction. CORS is disabled by default and exact-origin when enabled; defaults include Authorization, Request ID and Idempotency Key. Security headers include CSP, HSTS (also behind TLS termination), nosniff, frame denial, referrer, permissions and cross-origin resource policies. Swagger receives a narrowly relaxed CSP needed by its embedded UI. |
| Recovery and observability | Recovery converts panics to the common internal-error response without exposing the panic. Access logs and bounded Prometheus labels record route/status/duration and carry Request/Trace/Span correlation. |
| Tests | Tests cover accepted/generated Request IDs, content type, cancellation, login fail-closed limiting, CORS allow/deny, security headers, Swagger CSP, protected pprof and common 404/405/trailing-slash responses. Route-vs-Swagger invariants prove every registered business POST has a documented common success envelope. Targeted unit, race, vet and Swagger drift gates pass. |
| SOP applicability | Generic HTTP infrastructure performs no domain writes. Authentication/authorization, idempotency, rate limiting and domain logging decisions are separately audited because they have additional state and policy invariants. |

## Object storage and file audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Provider abstraction | `objectstorage.Store` is provider-neutral and the first adapters use the official AWS SDK v2 and Alibaba Cloud OSS SDK v2. Business file code depends only on the interface. Provider, bucket, region, endpoint and credentials are configuration-layer concerns; production custom endpoints require HTTPS and credential pairs are validated. |
| Input and resource bounds | Object keys, MIME types, metadata count/bytes and declared sizes are validated before SDK calls. Single PUT is capped at the providers' common 5 GiB ceiling; the file API additionally caps content by both `files.max_size_bytes` and the HTTP body limit, reads only that bounded amount, validates declared length, detects MIME and calculates SHA-256. Client filenames never become object paths. |
| Cancellation and privacy | Every provider operation combines caller cancellation with the configured one-second-to-five-minute storage timeout. A downloaded body owns that timeout until `Close`, rather than cancelling immediately after `Get` returns. Provider errors returned to tracing omit the object key, preventing tenant IDs or filename-derived data from becoming span error text. |
| Ownership and presentation | Metadata reads and mutations are tenant-scoped. Platform-owned records are additionally creator-scoped, preventing unrelated platform principals from sharing an implicit global file bucket. Records carry the canonical audit/version/delete fields and offset-aware timestamps. The API still returns `created_by` without a resolved display name, so the frontend presentation SOP is not yet satisfied. Resolution must use an owned projection or identity service API, never a cross-service database join. |
| Upload transaction | The object is written before metadata because the provider cannot participate in the SQL transaction. Metadata plus the successful operation event then commit atomically through `RecordTx`; any insert/log/commit failure attempts compensating object deletion. Failure events are recorded separately after rollback. A provider outage cannot create a successful metadata row. A failed compensation can still leave an unreferenced object, so bucket lifecycle or an inventory reconciliation path remains open operational work. |
| Download and deletion | A signed URL is disclosed only after its access event is durably accepted, so audit failure is fail-closed. Logical delete requires the submitted optimistic version and atomically stores its successful operation event. Physical object removal is an idempotent, per-file locked repair job; failure state, attempts and next retry live in the database and survive restarts, with bounded batches/backoff and a bounded detached repair context. |
| Cache, lock and authorization decisions | File metadata is not cached because signed access and deletion state are security-sensitive and the current access pattern does not justify staleness. Upload does not use a distributed lock because generated UUID identities and database uniqueness eliminate contention. Delete uses the narrow file-ID lock in addition to optimistic versioning and idempotent conditional updates. Route authorization remains owned by the shared database-policy interceptor. |
| Tests | Unit tests cover storage configuration, unsafe endpoints, timeout bounds, keys/MIME/metadata/size limits, timeout ownership through body close, upload validation/checksum, tenant and creator isolation, optimistic delete, durable retry, transactional log rollback plus object compensation, and fail-closed download logging. Database integration fixtures implement the transactional recorder contract. Real S3/OSS adapter integration tests are still missing and remain a verification gap. |
| Status | This category remains `in_progress` until creator display names, real-provider adapter integration coverage, and an orphan-object reconciliation/lifecycle decision are completed. |

## Health check audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Liveness semantics | `GET|POST /live` only reports that the process and HTTP stack can respond. It never calls the database, Redis or an upstream service, so a dependency incident cannot trigger a Kubernetes restart loop. |
| Readiness semantics | `GET|POST /ready` checks the enabled database and mandatory Redis concurrently. A disabled database is explicitly reported as `disabled`; absent or unhealthy Redis is always `down`. Any required dependency failure produces HTTP 503 and global error code `50003`. Success and failure retain `{code,message,body,request_id}`. Technical dependency errors are not disclosed. |
| Cancellation and bounds | Database and Redis receive separate child contexts, so a slow dependency does not consume the other's budget. Both configured timeouts must be positive and no greater than 30 seconds, and the request/stream parent Context still wins on client disconnect or deadline. The result channel has one slot per probe, preventing a completed probe from being stranded during cancellation. |
| Kubernetes contract | Startup and liveness probes call `/live`; readiness calls `/ready`. Probe timeouts exceed the shipped two-second dependency timeouts, startup has a bounded failure window, and readiness failure removes a Pod from service without restarting it. Both probe methods are accepted because Kubernetes uses GET while the platform's normal API convention is POST. |
| gRPC protocol | The maintained `google.golang.org/grpc/health` server owns `Check`, `List`, `Watch`, unknown-service `NOT_FOUND`/`SERVICE_UNKNOWN`, subscriber fan-out and shutdown semantics. A single lifecycle-managed worker publishes readiness for the overall server, application name and registered business service names once per second, avoiding one database/Redis poller per Watch client. Shutdown publishes `NOT_SERVING` before the gRPC server drains. Health methods bypass business authentication and database route authorization as infrastructure methods. |
| Tests | Unit tests cover dependency success/failure, disabled database, mandatory Redis, independent timeout, parent cancellation, no-dependency liveness, common HTTP envelopes and Request IDs, gRPC known/unknown service checks, List and streaming Watch. The integration-tag Testcontainers E2E suite checks HTTP live/ready and gRPC Check against PostgreSQL and Redis; it remains isolated to GitHub CI. |
| SOP applicability | Probes are read-only and intentionally anonymous. They do not cache results in the business cache, acquire distributed locks, write audit/security events, expose related IDs or mutate versioned rows. Dependency names and bounded latency are operational data; raw endpoints, credentials and errors are never returned. |

## Observability and diagnostics audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Metrics registry | Each application owns a private Prometheus registry rather than mutating the global registry. Metrics are exposed only when enabled and include Go/process collectors, HTTP and gRPC counts/latencies, outbound calls, Cron, SQL pool saturation, Redis pool activity, and shared cache/lock/rate-limit/idempotency/object-storage/event/log/lifecycle operations. Histograms are aggregatable server-side and the handler negotiates OpenMetrics. |
| Build identity | `service_build_info` is a single constant gauge labeled with service, active environment, packaged version, full Git commit and UTC build time. The same values are compiled into both binaries, image labels, root logs and the version endpoint; start time and uptime remain in the version endpoint rather than creating a changing metric label. |
| Cardinality | HTTP uses Gin route templates and maps unmatched paths to one label. gRPC accepts only methods derived from the registered Hello, Identity and Health descriptors plus the two exact reflection methods; every other client-supplied method becomes `unmatched`. Statuses are bounded HTTP codes/gRPC codes. Infrastructure component/backend/operation/status values are internal enums or validated providers. Outbound registries are capped at 100 per protocol and client names are bounded lowercase identifiers. IDs, keys, filenames, subjects, request paths and error messages are never labels. |
| Tracing setup | OTLP/HTTP tracing uses parent-based ratio sampling with finite ratio validation. The endpoint must be a bounded absolute HTTP(S) URL without embedded credentials, query or fragment. The provider merges the SDK default resource with service name/namespace, version, environment, commit and build time; shutdown flushes through the Fx deadline and restores prior global provider/propagator state. W3C Trace Context and Baggage are installed together. |
| Instrumentation coverage | `otelgin` and `otelgrpc` cover inbound HTTP/gRPC; `otelsql` covers PostgreSQL/Kingbase/MySQL; `redisotel` covers Redis; `otelhttp` and the gRPC client stats handler cover outbound calls. Cron, cache, distributed locks, idempotency and object storage create explicit spans with bounded attributes and error status. Object GET spans remain open through EOF/body close so streaming failures and duration are represented. |
| Async trace continuity | Outbox rows persist `traceparent` and `tracestate` atomically with the event. The dispatcher extracts the remote parent, creates a producer span, injects it through the shared JetStream SDK, correlates publish/release/mark-published SQL and logs, and ends the span on every success/error path. Consumers therefore continue the originating trace even though delivery occurs after the request transaction. |
| Log correlation and privacy | The shared slog handler adds valid Request ID, Trace ID and Span ID from Context unless already bound, preventing duplicate JSON keys. HTTP/gRPC, Cron and asynchronous paths use context-aware logging. Authorization headers, tokens, cache/lock keys, object keys and payload bodies are excluded from ordinary telemetry; provider errors exported to spans omit object keys. |
| Diagnostics security | pprof is disabled by default. Enabling it requires a 32-4096-byte independent token; every actual pprof route uses a constant-time Bearer comparison and unauthorized responses disclose no diagnostic data. Production Swagger separately requires authentication. Metrics remain intended for the cluster monitoring plane and Kubernetes NetworkPolicy limits the service ports to in-cluster sources. |
| Tests | Tests gather custom/build/SQL/Redis metric families, prove unknown gRPC methods collapse, verify default/custom OTel resources and propagation fields, hold object GET telemetry until body close, round-trip Outbox W3C parent context, correlate structured logs without duplicate fields, and exercise the real protected pprof route. Full unit, race, vet, lint and generated-contract gates are required locally; Testcontainers remains GitHub-CI-only. |
| SOP applicability | Telemetry is observational and must never authorize a request or become a correctness boundary. It does not replace operation/security logs, database transactions, optimistic versions, locks or tenant SQL predicates. Telemetry failures may drop signals during shutdown/export failure but cannot change a committed business result. |

## Scheduler and data lifecycle audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Scheduler engine | The mature robfig/cron v3 engine parses six-field schedules in the configured IANA timezone, recovers panics and skips local overlap. Timezone/schedule strings and job timeout are bounded before runtime; constructor parsing still fails startup for an unknown timezone or invalid expression. Scheduler start/stop is owned by Fx. |
| Shared job context | `runJob` is the required execution seam for scheduled work. It derives a bounded Context from the scheduler lifecycle, injects `<service>:scheduler:<job>` as a system principal plus a generated Request ID, opens an OTel span, and passes that same Context into the callback. Application shutdown cancels running callbacks before waiting for cron, so a long job cannot outlive graceful shutdown merely because its configured timeout is longer. |
| Cross-replica coordination | Every job uses the platform SDK's renewable Redis lease and the configured global lock TTL with a job-scoped key. Local overlap is also skipped before distributed work begins. Contention is an explicit `skipped` metric result; Redis/acquisition/renewal failure fails closed, lease loss cancels callback work, and release remains ownership-safe. The durable operation itself must still be idempotent and database-constrained. |
| Job telemetry | Each run records bounded job/status counters and duration histogram. Context-aware logs inherit Request/Trace/Span IDs and system identity. Panics are recovered by the scheduler chain; ordinary errors are recorded on the span and logged once by the runner. No user-controlled job name reaches a metric label in the shipped registry. |
| Lifecycle coordination | Data maintenance first acquires the service/environment Redis lease, so PostgreSQL, Kingbase and MySQL replicas share one active worker. PostgreSQL/Kingbase additionally use a transaction-scoped advisory lock whose identity contains service, database and schema, retaining correctness if the Redis lease is lost. Startup contention is a safe skip; Redis or SQL failure is not treated as success. |
| Time and partition policy | Retention boundaries and names use a fixed Asia/Shanghai `+08:00` month start. Only owned `operation_logs_yYYYYmMM` and `security_logs_yYYYYmMM` children are eligible. Current plus configured future months are ensured. Before creating a missing partition, maintenance checks its default-partition range and fails rather than silently moving or stranding rows. Identifiers come only from validated fixed table/schema names and are quoted. |
| Retention and archive | An expired partition is detached atomically, then either moved to the validated archive schema or dropped only when archive configuration is explicitly empty. Production defaults to a service-specific archive schema. The runtime/migration role must be deliberately granted partition/archive DDL; this is an operational privilege, not inferred from ordinary CRUD. MySQL has no equivalent detach and instead performs stable `occurred_at,id` deletes with a bounded batch size and bounded maximum batches per run, allowing backlog catch-up without an unbounded transaction. |
| Bounds and shutdown | Lifecycle interval is 1 minute-24 hours. Each run timeout is 1 second-30 minutes and must be below the interval; premake, retention, batch size/count and archive identifier are bounded. The background worker is cancel-and-join managed, uses a reusable ticker, and every SQL/lock call receives the lease/lifecycle Context. |
| Audit/cache/authorization decision | These are infrastructure jobs, not user-facing interfaces, and do not read or return tenant data. They use explicit system identity and structured/metric/trace evidence. They deliberately do not write operation/security rows about retention of those same logs, avoiding recursive audit generation and a false atomicity claim. No result cache, optimistic row version or HTTP permission expression applies; distributed/advisory locks and SQL ownership filters are the relevant controls. |
| Tests | Scheduler tests cover Redis failure, contention, acquired execution, system principal, Request ID, deadline and shutdown cancellation. Lifecycle tests cover +08 month boundaries, owned-name parsing, default-partition refusal, archive/drop eligibility, system context, contention skip and bounded multi-batch MySQL deletion. PostgreSQL/MySQL Testcontainers validate partition routing/premake and physical retention; integration tests remain GitHub-CI-only. |

## Distributed cache audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Shared contract | Business services constructor-inject the platform SDK's backend-independent `cache.Store`; the local package only re-exports that contract and adds configuration, metrics and traces. No business module depends directly on `redis.Client`. |
| Namespace and bounds | The effective prefix is always `<environment>:<service>:` (or `<environment>:<explicit-prefix>:`), so services and profiles sharing a Redis deployment cannot collide. Resource keys contain a schema version and tenant ID where the resource is tenant-owned. The shared adapter bounds keys to 1024 bytes, qualified keys to 2048 bytes, values to 16 MiB and batch deletion to 1000 keys. Configured cache TTLs are positive and at most 24 hours; Redis dial/read/write timeouts are positive and at most one minute. |
| Cached data | Identity user lookups, a tenant's own root record, pre-authorization menu tree sources and public platform configuration are read-heavy derived data. Menu authorization remains principal-specific after loading the shared source, so no principal-filtered response is cached globally. Authentication login status bypasses the identity cache and reads the authoritative database. |
| Miss and stampede policy | Not-found results are deliberately not cached, avoiding stale negative entries after creates. Penetration is bounded by authentication plus global/login rate limits and indexed exact lookups. No distributed read lock is used: cache loss may increase bounded database load but must not turn a Redis outage into read unavailability; SQL pool bounds and menu `max_nodes` provide backpressure. |
| Consistency and failure | The database is authoritative. Cache read/decode/write failures fall back to or retain the database result. Successful mutations commit first and then delete every affected key. Post-commit invalidation preserves request correlation while ignoring client cancellation and has a fixed three-second deadline; failed transactions do not invalidate. A failed invalidation permits bounded staleness only until the configured TTL. Security decisions do not accept that staleness. |
| Sensitive data and observability | Cache operations emit OpenTelemetry spans and low-cardinality Prometheus dimensions for backend, operation and status; keys, IDs and values are excluded from metric labels. Identity cache failures no longer log username-bearing keys. Public configuration rejects secret-like keys and nested values before they can be cached. |
| Tests | Unit tests cover SDK key/value/TTL/delete validation, JSON helpers, environment namespace separation, request-cancellation-detached invalidation context, dual identity keys, failed-mutation preservation, bounded configuration and authoritative login status. The integration-tag Redis Testcontainers suite covers cache set/get/delete against Redis. |
| SOP applicability | Cache reads do not create business mutations, audit rows or permission grants. Authorization and tenant SQL filtering happen before or after cache access as appropriate; optimistic locks and operation/security logs remain owned by the mutation paths. |

## Distributed lock audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Shared implementation | The template re-exports the platform SDK's `distlock.Locker` and lease helpers; the Redis implementation uses the mature Redsync component. Services constructor-inject `cache.Locker` and do not implement token, renewal or Lua ownership logic locally. Redis is mandatory and is pinged before transports start. |
| Namespace and validation | Lock keys share the mandatory `<environment>:<service>:lock:` prefix. The SDK rejects blank, whitespace/control-character and over-1024-byte keys. The independent `distributed_lock` configuration requires a TTL from 300 ms through 5 minutes and a retry delay from 10 ms through 5 seconds that is shorter than the TTL. |
| Granularity | Membership creation locks one tenant/user pair; platform configuration locks one configuration key; deletion repair locks one file; scheduler leadership locks one job; department membership locks one department while tree topology uses the tenant tree; menus use the global menu tree because parent-cycle validation spans that tree. Tenant authorization keys scope to the ceiling, administrator, role or member-role invariant being changed. No service-wide mutation lock is used. |
| Lease lifecycle | `WithLock` and `TryWithLock` renew every TTL/3. The callback must use the supplied lease Context; renewal failure cancels it with the ownership-loss cause. Unlock uses a cancellation-detached Context bounded by the lesser of TTL and five seconds and verifies the ownership token. Call sites were audited to propagate the lease Context without overwriting the outer request Context; this prevents a successful commit from being followed by a false `context canceled` response. |
| Failure and durable safety | Contention and Redis/lease failures fail closed for invariant-sensitive mutations; scheduled contention is an explicit skipped result. Locks are not the sole correctness boundary: unique constraints prevent duplicate membership/configuration codes, serializable transactions protect graph/set replacements, and update/delete operations retain optimistic versions. Consequently a paused process or expired lease cannot silently overwrite a newer durable version. |
| Observability | Acquire, try, extend and unlock operations emit low-cardinality Prometheus dimensions and OpenTelemetry spans with success, contention or error status; raw keys and IDs are not labels. Cron additionally distinguishes success, skipped and failed runs. |
| Tests | Local tests cover validation, prefixing, contention, ownership-safe unlock/reuse, explicit extension, lease-loss cancellation and preservation of the caller Context after a lease ends. The integration-tag Redis Testcontainers suite proves cross-client contention and automatic renewal against Redis. |
| SOP applicability | Lock helpers do not authorize requests or write audit records. Each protected service operation performs authorization and operation/security logging in its own callback and uses the lease Context for all SQL, Redis and upstream work. |

## Idempotency audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Shared state machine | HTTP and unary gRPC delegate ownership transitions to the pinned platform SDK. Redis Lua scripts atomically acquire, renew, complete, fail or abort only for the current unguessable owner. Processing, completed, failed and conflicting states have explicit HTTP/gRPC mappings. Streaming RPCs do not execute the unary idempotency state machine. |
| Route policy | Only explicitly configured POST mutation routes participate, and clients must supply a syntactically bounded key. The shipped list excludes all queries plus login/refresh, secret-returning service-account calls, file upload/download and arbitrary platform-configuration values. Validation rejects those routes even when included by a wildcard. The sample gRPC list is empty until a real mutation RPC is added; health and example ping calls are not misused as cacheable mutations. |
| Fingerprint and isolation | Canonical JSON and deterministic protobuf bytes are combined with operation, principal type/ID, tenant, membership and session. The local adapter additionally scopes that digest to environment and application. Storage keys use the mandatory environment/service Redis namespace, while the independent fingerprint scope prevents a deliberately shared custom prefix from replaying another service's result. |
| Ownership and cancellation | `processing_ttl` is bounded from one second through 15 minutes and must exceed the HTTP request timeout. A lease renews at one third of that TTL. The lease Context replaces the HTTP/gRPC business Context, so Redis failure or ownership loss cancels context-aware SQL, Redis and upstream work; completion and failure still reject a stale owner. Persistence uses a cancellation-detached two-second Context after the handler finishes. |
| Replay and failure bounds | Completed results live from one minute through seven days; deterministic failures from one second through 24 hours. HTTP capture and Redis persistence are both bounded by `max_response_bytes` (at most 16 MiB); an oversized response releases ownership immediately. HTTP 408/425/429/5xx and retryable gRPC codes abort rather than cache transient failure. HTTP replay substitutes the current Request ID. No credentials, tokens, cookies or signed URLs are retained. |
| Durable correctness | Redis is mandatory and idempotency fails closed when its state cannot be read or leased. The business transaction commits before completion is recorded, so every configured mutation must still rely on its reviewed transaction, unique constraints, optimistic version and narrowly scoped distributed lock where applicable. Redis idempotency is not represented as an atomic database/Redis commit. |
| Observability | Begin, complete, fail, abort and lease operations emit OpenTelemetry spans and bounded infrastructure metrics. Status and operation are labels; idempotency keys, request payloads, principals and response bodies are never labels or log fields. Lease/persistence failures retain Request/Trace correlation through context-aware logging. |
| Tests | Local tests cover canonical JSON, tenant/principal dimensions, current-Request-ID replay, processing/conflict/failure mappings, retryable abort, bounded capture, environment namespace separation, service-scoped fingerprints, stale owners, expiry and lease-loss cancellation. The integration-tag Redis Testcontainers suite covers contention, conflict, completion/replay and renewal against Redis; the pinned shared SDK supplies HTTP-independent unary-gRPC protobuf contract tests. |

## Outbound HTTP/gRPC client audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Ownership and construction | The Fx registry creates one bounded set of named HTTP clients and gRPC connections, reuses their pools, closes idle HTTP connections and gRPC connections during reverse-order shutdown, and cleans already-created clients when a later constructor fails. Direct constructors repeat safety validation so package callers cannot bypass registry configuration bounds. |
| Deadline and cancellation | HTTP and unary gRPC apply one configured deadline around the complete logical call, including all retries and backoff; a shorter parent deadline wins. HTTP binds cancellation to response-body EOF/close so returning a response does not prematurely break streaming reads, while an abandoned body remains bounded by the deadline. gRPC streams deliberately require a caller-owned deadline because a fixed unary budget is unsafe for long-lived streams. All transports consume caller/lease cancellation. |
| Authentication and TLS | Named clients support Bearer or PSK and replace any caller-supplied authorization value instead of appending ambiguous credentials. Credentials require TLS except for the explicit non-production plaintext opt-in; production rejects that opt-in. TLS requires paired mTLS files, TLS 1.2+, bounded paths/server names, and extends the system root pool with a private CA. HTTP rejects non-HTTP schemes, URL userinfo/query/fragment, does not echo credential-bearing URLs in errors, and never follows redirects automatically. |
| Retry and breaker safety | Attempts are capped at five with bounded equal-jitter exponential backoff. HTTP retries only RFC-idempotent verbs or calls carrying the shared idempotency key; unary gRPC retries only reviewed bounded method patterns or an idempotency-protected call. Only transient HTTP 429/502/503/504 and gRPC Unavailable/ResourceExhausted results retry. Breakers use bounded thresholds/open durations and observe the exhausted logical call. Streaming RPCs are not transparently replayed or circuit-broken. |
| Discovery and pooling | gRPC targets use the registered resolver and round-robin service config, so targets such as `dns:///inventory:9090` can resolve multiple endpoints without generated service-specific client wiring. HTTP uses the standard DNS resolver, proxy policy, HTTP/2 and bounded reusable connection pools. More advanced discovery remains an adapter concern behind the registry. |
| Context and observability | HTTP propagates Request ID and idempotency headers; gRPC propagates the matching metadata for unary and streaming calls. OpenTelemetry instruments both transports. Prometheus unary metrics use only protocol, a validated bounded client name, status and duration; targets, credentials, method names, payloads, tenants and principals never become labels. |
| Tests | Unit and race tests cover safe HTTP/gRPC retry eligibility, breaker opening, configured-vs-caller deadline precedence, HTTP response-body lifetime, Request ID/idempotency propagation, configured authentication replacement, redirect refusal, unsafe URL/TLS/policy rejection and direct gRPC dial bounds. Configuration tests cover startup-level bounds and production plaintext rejection; full local generation/lint/vet/race gates are required before each audit commit. No external database or Redis behavior is involved, so Testcontainers is not applicable to this transport-only contract. |
| SOP applicability | Outbound infrastructure performs no local domain mutation, database auditing, cache write, tenant filtering or permission decision. The calling business operation remains responsible for authorization, operation/security logging, idempotency, tenant scope, transaction boundaries and display-ready response mapping. |

## Operation log and frontend event audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Durable async path | `Record` no longer publishes directly to NATS. It builds a versioned protobuf envelope and commits it to the service-owned transactional outbox with a cancellation-detached three-second deadline. The dispatcher retries with leases/backoff and dead state; JetStream performs event-ID de-duplication and its durable consumer retries then emits the shared dead-letter event. `RecordTx` accepts a caller-owned transaction for atomic domain-write/log acceptance. |
| Record contract | Records contain tenant and actor, application/resource/operation, source/protocol/method/route, request summary, duration/result/error, Request/Trace IDs, client IP, user agent, extension and occurrence time. Required and attacker-influenced strings, durations, UTF-8 and payload sizes are bounded. Events with an unsupported version, invalid timestamp/JSON or mismatched envelope identity/context are rejected before persistence. |
| Privacy | Request and extension JSON pass through the shared recursive credential redactor. Oversized request JSON becomes a small valid JSON truncation marker; extension JSON fails closed rather than being partially stored. Raw authorization headers, cookies and tokens are not accepted as explicit fields. Clear client IP and user agent are intentionally retained for the requested troubleshooting purpose and are protected by route authorization, tenant SQL predicates and lifecycle retention. |
| Frontend ingestion | Only authenticated `menu_view` and `button_click` events are accepted. Event/name/route/duration/error/extension fields are bounded; actor, tenant, IP, user agent, Request ID and Trace ID come from trusted server context. The route is configured for idempotency so a client retry cannot enqueue a second event with the same key and payload. |
| Persistence and delivery | `operation_logs` is append-only at the API layer, uses the common audit/version/delete columns and is partitioned monthly for PostgreSQL/Kingbase with BRIN and tenant/time/resource/application/request indexes; MySQL uses matching composite indexes and bounded retention deletion. The event ID is the insert idempotency key, so consumer redelivery is a no-op. Cache, distributed lock and optimistic-update concerns are not applicable to an append-only insert stream. |
| Query isolation and presentation | Get/page require a principal. Tenant principals always receive an SQL `tenant_id` predicate and cannot override it with submitted tenant IDs; platform principals may explicitly filter tenants. Filters and IN lists are bounded, occurrence time uses a half-open range, and ordering is stable by occurrence/id. Reads enqueue their own operation event because payload, IP and user-agent fields are sensitive. Timestamps are native offset-aware values under the platform's Asia/Shanghai database/session policy. |
| Observability and tests | Database enqueue and consumer persistence expose low-cardinality infrastructure metrics; event processing propagates Request/Trace context and failures enter the common retry/dead-letter path. Unit tests cover redaction, valid bounded truncation, detached durable enqueue, caller transaction use, malformed context rejection, field limits and tenant SQL isolation. Database Testcontainers cover idempotent append-only inserts, audit triggers, partitions and retention. |
| Open work | Several domain services still wrap already-committed mutations with the legacy non-transactional `Do` helper. Their successful operation events must be moved to `RecordTx` inside the corresponding domain transaction; failed attempts must remain separately recordable after rollback. This category stays `in_progress` until those call sites are migrated during their domain audits. |

## Security log audit decisions

| Concern | Current decision and evidence |
| --- | --- |
| Independent durable path | Security events use a distinct recorder, subject, durable consumer and `security_logs` table. Standalone `Record` commits to the database outbox with a cancellation-detached three-second deadline; `RecordTx` stores in the caller's transaction. Both paths therefore precede asynchronous JetStream delivery and use the shared bounded retry/dead-letter behavior. Production configuration requires this chain and fail-closed behavior. |
| Authentication lifecycle | User login success/failure counters, refresh rotation/reuse, logout, password reset/change, session revoke and all-session revocation store the event in the same transaction as credential/session state. Anonymous login is explicitly supported: the event actor remains empty, while the outbox row uses a service system actor solely for database audit triggers. Handlers record remaining rejected attempts with stable safe error codes rather than raw technical errors. |
| Privacy and attribution | Login identifiers are normalized and HMAC-SHA256 hashed with a dedicated 32-4096-byte secret; opaque token/JTI values are separately HMAC hashed without normalization. Token hashes are omitted from API JSON. Metadata must be a bounded JSON object and is rejected if the shared recursive detector finds password, secret, token, authorization, cookie or API-key fields. IP, user agent, Request/Trace IDs, tenant and subject/session IDs are retained for the explicitly requested investigation trail. |
| Envelope and persistence safety | Producers bound UTF-8 identity/session/reason/error/client fields. Consumers require schema version 1, a valid matching timestamp, matching tenant/actor/request/trace envelope context, known event type, bounded hashes and object metadata. Event ID plus occurrence time provides PostgreSQL/Kingbase redelivery idempotency; MySQL uses the event ID primary key. Invalid events enter retry then dead letter rather than partially persisting. |
| Query isolation | Get/page require a principal. Tenant callers always receive an SQL tenant predicate and submitted tenant IDs cannot widen it; platform callers may explicitly filter. ID/event/session/request/IP lists, identifier lookup, keyword and half-open time range are bounded. Security-log reads enqueue `security_log_accessed` before returning data and fail closed if that durable acceptance fails. Token hashes are never returned. |
| Storage lifecycle and observability | The append-only table has common audit/version/delete fields, monthly PostgreSQL/Kingbase partitions, BRIN and tenant/time/actor/subject/event/request indexes, plus MySQL equivalents. Database enqueue/persist metrics use bounded labels; Request/Trace linkage stays in event fields and logs. Retention is owned by the separately audited data-lifecycle worker. Cache, distributed locks and optimistic updates are not applicable to append-only ingestion. |
| Tests | Unit tests cover keyed/normalized hashing, credential metadata rejection, object-only metadata, anonymous and canceled-request durable enqueue, caller-transaction use, malformed envelope context, field limits and tenant SQL isolation. Authentication tests prove domain rollback when transactional security storage fails. Database Testcontainers cover audit triggers, idempotent insertion, partitions and retention. |
| Open work | Identity-user and service-account administrative mutations and login attempts now use `RecordTx`. Several tenant/authorization/menu/configuration mutations still call standalone `Record` only after their domain transaction. They survive JetStream outages, but are not atomic with that mutation. Those call sites must move to `RecordTx` during their owning domain audits before this category becomes `verified`. |
